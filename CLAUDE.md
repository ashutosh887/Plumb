## Project: Plumb

Plumb is a signer-side transaction inspector for Squads V4 multisig approvals. Browser extension intercepts the approval flow, decodes the tx, and surfaces three classes of finding: durable-nonce replay risk, multisig admin actions, and (when applicable) BPF program-upgrade authority changes. Plumb is **read-only at the signer interface**.

Built for the **Solana Frontier Hackathon** (Colosseum, runs 2026-04-06 → 2026-05-11). Targeting **Grand Champion + Cohort 5**, not Public Goods.

> Origin story (locked Draft A — use verbatim): *"I was scoping a Solana treasury setup with Squads in late March. April 1 hit. I read every Drift post-mortem and realized: I was about to be one of those signers — staring at base64 I couldn't decode, trusting the deployer's PDF. I built Plumb because I refuse to be the next signer who gets socially engineered."*

## Operating principles (read once, hold throughout)

1. **Demo > production.** Every decision optimizes for a 90s video that wins. If a feature doesn't appear on screen in those 90 seconds, it ships post-hackathon.
2. **Three features only.** Durable-nonce decoder, state-projected simulation, BPF program-upgrade diff. **No fourth feature without explicit user approval.**
3. **Visible work compounds.** Public repo from commit zero, public devlog tweets at every milestone. Judges Google-search names; surface area matters.
4. **Resist platform syndrome.** When in doubt, cut scope.
5. **Origin story is the weakest leg.** Front-load it (locked above).

## What Claude must NEVER do

- **Never modify a user's transaction.** Plumb is read-only at the signer interface. The moment Plumb writes, it becomes the attack surface.
- **Never add a fourth feature without explicit approval.**
- **Never pitch Plumb as a "platform" or "suite."** It is a seatbelt.
- **Never claim Plumb would have caught Drift specifically.** Claim Plumb would have *surfaced the warning signs the signers missed*. Slightly weaker, much more defensible.
- **Never use the words** *revolutionize, democratize, empower, ecosystem-wide* in any user-facing copy. Mert closes the tab.
- **Never ping Matty Tay or Toly without a finished demo in hand.**
- **Never reference unrelated projects** (sibling repos, other prior work) when shaping Plumb's narrative or origin. Plumb is the only project in scope.

## Scope (in / out)

**In (MVP):**

1. **Durable-nonce decoder + multisig admin-action flag.** First-IX `AdvanceNonceAccount` detection, owner-mismatch on the nonce account, replay-window estimate, Squads admin-action discriminator classification.
2. **State-projected simulation.** Surfpool mainnet fork, `simulateTransaction`, account/balance/authority diff in plain English.
3. **BPF diff for program upgrades.** When the tx is `BpfLoaderUpgradeable::Upgrade`, disassemble old + new ELFs via `solana_rbpf`, surface signer-check and authority-check changes.

**Out (v2, post-hackathon):** risk scoring engine, Slack alerts, multi-sig coordination view, Ledger pre-sign, post-mortem replay. Do not build them. The temptation will be strong.

## Architecture decision: client-side decode

The extension does decode + risk assessment inline (`apps/extension/lib/inspect.ts` calls `@plumb/core` directly). No network round-trip to a server during demo. This is the right shape for a read-only signer-side tool — no extra trust surface, no operator dependency, no demo-day flake from a flaky localhost service.

For the BPF diff, the demo fixture ships with a **pre-baked diff JSON** in `fixtures/drift_admin_transfer.json` under `meta.bpfDiff`. The Rust crate generates the equivalent output for real ELF inputs and stays available for v2.

## Common commands

The demo runs from **just two processes**: the dashboard and the extension. No Python and no Rust binary required for the demo recording — decoding + risk assessment happen client-side in the extension via `@plumb/core`. The FastAPI service is reserved for v2 server-side state-projected sim, the Rust BPF crate is reserved for real ELF disassembly later.

```sh
pnpm install
pnpm fixtures             # build real base64 tx fixtures (drift + clean)
pnpm --filter @plumb/dashboard dev   # http://localhost:3000/demo
pnpm --filter @plumb/extension dev   # opens Chrome with extension loaded
pnpm test                 # vitest — should report 6 passing
pnpm typecheck            # all 4 TS workspaces clean
pnpm build                # extension + dashboard production builds
```

Single-test invocation:

```sh
pnpm --filter @plumb/core test -- risk.test.ts
pnpm --filter @plumb/core test -- e2e_drift.test.ts
```

For v2 / server-side work (not needed for hackathon demo):

```sh
cargo build --release -p plumb-bpf-diff   # needs Rust toolchain
cargo test -p plumb-bpf-diff
# FastAPI requires Python 3.11+; system python3 may be too old.
# If/when needed: pyenv install 3.11 && cd services/api && python -m venv .venv && .venv/bin/pip install -e ".[dev]"
```

## Drift attack — what Plumb claims, precisely

Plumb defends against the *class* of attack. It would have surfaced four warning signs on the actual Drift pre-sign txs (durable-nonce flag, owner mismatch, multisig admin action, replay-window). Whether the signers would have stopped is a human question. **Do not over-claim.** See `RESEARCH.md` §1.1 for sourced detail.

The Drift migration was **2026-03-26**, not March 27. Use March 26 in fixtures, demo script, and any external copy.

The Drift attack vehicle was a **multisig admin transfer via durable nonce** — *not* a BPF program upgrade. The BPF-diff frame in the demo is positioned as the *next class of attack*, not as what would have caught Drift specifically.
